# Key continuity: upgrades, failover, and recovery

How encrypted volumes survive upgrades, replicate for failover, and recover from disaster — without the operator ever holding a decryption key (unless they voluntarily request a break-glass recovery key, which still requires attestation to use).

## The two-dataset model

Each Safebox volume contains two ZFS datasets:

- **`safebox-pool/data`** — the bulk content (database, app state, user files, tenant datasets). Encrypted with a per-instance data key (AES-256-GCM, ZFS native encryption).
- **`safebox-pool/keys`** — a small bootstrap dataset (kilobytes: key material, manifests, identity). Encrypted under the attestation-bound root via TPM2 PolicyAuthorize, meaning only a Safebox whose measurement has been M-of-N-blessed by the auditor quorum can mount it.

The key dataset is the bootstrap: whoever has it and can prove attestation can mount everything. The data key (for `safebox-pool/data`) lives *inside* `safebox-pool/keys`. So the unlock sequence is always:

1. Prove attestation (blessed measurement + M-of-N signature).
2. TPM releases the key for `safebox-pool/keys`.
3. Read the data key from `safebox-pool/keys`.
4. Mount `safebox-pool/data`.

This means the key material *travels with the data* — any replica, snapshot, or volume copy automatically contains everything needed to mount, gated only by attestation.

### What lives in the key dataset

- The ZFS encryption key for `safebox-pool/data`.
- Per-tenant dataset encryption keys (if per-tenant ZFS datasets are used).
- Manifest hashes for mounted model/runner volumes (what is authorized to load).
- The Safebox's persistent identity material (customer config, BYO-key references, app-layer blessing digests).
- The break-glass recovery blob (if the operator requested one — see below).

This dataset is tiny (a few KB) but is the complete bootstrap for the full identity.

## Three scenarios, one mechanism

All three are "attest + mount the key dataset + read the data key + mount the data." The difference is how the volume got there.

### Upgrade (same machine, new image)

Boot the new NixOS generation on the same volume. The new image's measurement is blessed; the TPM releases the key dataset's key; both datasets mount. No data copy. Rollback is identical: boot the old generation (still blessed), same volume, same mount path. The ZFS data format is version-independent — a pool created by one generation mounts fine on another (do not enable new ZFS pool features until all fleet members support them).

### Failover (replica on another machine)

The standby has both datasets, received via `zfs send -i -w` (incremental, raw/encrypted — the standby stores ciphertext without the key). On failover: the standby proves attestation → the key dataset decrypts → the data key is read → the data mounts. No operator, no transfer token, no external key-release service. The replica already has everything; attestation is the only gate.

For same-cloud failover, cloud-level volume operations (EBS snapshot → create volume → attach) are even faster — the cloud copies at the block layer, and the new Safebox attests and mounts.

### Break-glass recovery (volume orphaned, no replica, no live instance)

This is the emergency path for the genuine edge case: the instance is dead, no replicas exist, and the volume sits with encrypted data and no live Safebox to hand off from. For this case, and ONLY this case, the operator can *voluntarily request* a recovery key — see the section below.

## Replication via ZFS send

`flush-and-snapshot.sh` (already built) takes a clean snapshot (FLUSH TABLES WITH READ LOCK, 1-5s window). Then:

```
# initial full send (both datasets, encrypted)
zfs send -w safebox-pool/keys@snap1 | <transport> | zfs receive safebox-pool/keys
zfs send -w safebox-pool/data@snap1 | <transport> | zfs receive safebox-pool/data

# incremental (only changes since last snapshot — block-level delta)
zfs send -i @snap1 -w safebox-pool/data@snap2 | <transport> | zfs receive safebox-pool/data
```

The `-w` (raw) flag sends encrypted blocks. The receiving side stores ciphertext without the key — it cannot read the data until it proves attestation and mounts the key dataset.

This is more efficient than rsync (block-level, not file-level) and works cross-account, cross-region, and cross-cloud. The transport between two sealed Safeboxes (no SSH) is an application-level encrypted channel provided by the system component.

Model/runner volumes do not need ZFS send — the standby re-fetches them from the model supply chain using the same signed manifests, verified by SHA-256 hash.

## Break-glass recovery (HKDF, operator-requested)

The break-glass recovery key is **voluntary** — the operator explicitly requests it, and the Safebox records that they did. It is NOT generated by default. The design:

### Generation (on operator request)

1. The operator sends a governed request ("generate recovery key") to the live Safebox.
2. The Safebox logs the request (who, when, from which IP) in the key dataset — this is auditable and survives replication.
3. The Safebox derives a recovery key: `recovery_key = HKDF-SHA256(master_secret, "recovery" || instance_id || timestamp)`.
4. The Safebox wraps the data key under a two-factor construction: `wrapped = Encrypt(KDF(recovery_key, attestation_context_template), data_key)`. The `attestation_context_template` is the auditor quorum's public key hash — the same root that governs PolicyAuthorize.
5. The wrapped blob (with an expiry timestamp, e.g., 30 days) is stored in the key dataset.
6. The recovery key is displayed ONCE to the operator (as a passphrase, QR code, or file download), then discarded from memory.

### Use (on recovery)

1. The operator inputs the recovery key into a NEW, freshly-booted, blessed Safebox with the orphaned volume attached.
2. The new Safebox proves its attestation (blessed measurement), producing the attestation context.
3. The new Safebox combines the recovery key + its attestation context via the same KDF to derive the unwrapping key.
4. The new Safebox checks the expiry timestamp — if expired, it refuses.
5. The new Safebox unwraps the data key, mounts both datasets, and becomes the primary.

### Safety properties

- **Neither factor alone suffices.** The recovery key without an attested Safebox cannot produce the attestation context → cannot derive the unwrapping key. An attested Safebox without the recovery key cannot derive the unwrapping key either. Both are required.
- **The operator cannot read the data with just the key.** Even if the key leaks, it is useless without a blessed Safebox — and the operator does not control what is "blessed" (the auditor quorum does). This is the property that makes operator-held keys safe: the blast radius of a leaked key is bounded by attestation.
- **Quantum-resistant.** HKDF-SHA256 is symmetric; no RSA/EC in the critical path. Grover's algorithm halves the effective key length, so 256-bit HKDF gives 128-bit post-quantum security — the standard target.
- **Expiry.** The wrapped blob has a baked-in timestamp; after expiry (configurable, default 30 days), the recovery key is useless.
- **Auditable.** The Safebox logs the recovery-key request in the key dataset. Anyone with attestation who mounts the key dataset can see that a recovery key was generated, when, and by whom. This survives replication — replicas also carry the audit record.
- **Voluntary.** The Safebox does not generate a recovery key unless explicitly asked. Deployments that replicate (and thus don't need break-glass) never generate one.

## Backward compatibility and mixed fleets

The ZFS data format is version-independent. A pool created by NixOS generation N mounts on generation N+1 and vice versa. The PolicyAuthorize blessed-measurement set contains ALL currently-blessed versions, so:

- Version N can decrypt (its measurement is blessed).
- Version N+1 can decrypt (its measurement is blessed).
- Rollback to N works (N is still blessed — unless explicitly revoked for a security fix).
- A standby on N can receive replication from a primary on N+1 and mount it.

The only constraint: do not enable new ZFS pool features in an upgrade until all fleet members (including standbys) support them.

## Explicit revocation (forced security upgrades)

If an upgrade fixes a critical vulnerability and rollback must be prevented, the auditor quorum removes the old measurement from the blessed set. The old image can no longer satisfy PolicyAuthorize → the TPM refuses to release the key dataset's key → the old image cannot decrypt the data. This forces the upgrade: only the patched version (or newer) can access the data.
