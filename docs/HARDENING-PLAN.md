# Hardening Plan: Closing Every Path Into a Production Safebox

This document is the specification that the build scripts, initramfs modules, Terraform modules, and red-team tests are checked against. It exists because an adversarial review of the first multi-cloud build found that an attacker with ordinary administrative access to the cloud account could still get root on a production safebox on all four clouds. The findings and the fixes are listed here, followed by the implementation contract that every component follows.

## What the review found

The build removed sshd, the SSM agent, the GCP guest agent, and the OCI cloud agent, and disabled login prompts. That was necessary but not sufficient. The following paths remained open on all four clouds unless noted.

The root filesystem was writable, unmeasured, and held secrets. An attacker could snapshot the boot disk, mount it on another VM, add a systemd unit, and swap the disk back. Attestation checked only PCR 0 and 7, which do not change when the root filesystem changes. The virtual TPM stays with the VM across a disk swap, so any key sealed to those PCRs would still unseal.

cloud-init was installed and unrestricted, so anyone who could launch an instance from the golden image could pass a script as user-data and get root on first boot. The Azure and OCI images also still contained the build operator's account with passwordless sudo.

There was no GRUB password, so anyone who reached the serial or VNC console could add `init=/bin/bash` to the kernel command line. Secure Boot does not prevent this. Nothing in the Terraform disabled the consoles at the cloud level.

Azure extensions (Run Command, VMAccess) were blocked only by an unverified edit to `waagent.conf`, not by removing the agent or by the Terraform flags that disable extension operations.

`safebox-infra`, the user the system component runs as, was in the `docker` group, which is root-equivalent on its own. The sudoers file also allowed `docker run --detach *` with any flags and `dnf install -- *` with any package. A compromised tenant container holding its HMAC key could become host root and reinstall anything that had been removed.

Containers could reach the cloud metadata service and read the account token. OCI also left the legacy v1 metadata endpoints on.

The HMAC master key was stored on the unencrypted root disk and read from there before any attestation ran. On AWS the attestation client needed `/dev/nsm`, which exists only inside a Nitro Enclave that was never launched, so it fell back to random bytes. On Azure and OCI the attestation client was never linked in, with the same result. On GCP the key was derived from PCR 0 and 7 alone, which are the same on every Shielded VM. The ZFS key was never sealed to the TPM at all; the sealing script did not exist in the repository.

One more problem surfaced while implementing the fixes rather than during the review. The design below depends on Secure Boot staying enabled, because the PCR 7 measurement and the kernel lockdown mode both assume it. With Secure Boot on, the kernel loads only modules signed by a key in its trust store, and the ZFS module is out of tree. On Amazon Linux 2023, Debian 12, and Oracle Linux 9 the ZFS module is built locally by DKMS or shipped unsigned, so it either fails to load under Secure Boot or requires enrolling a self-made MOK, which puts a private key on the build host and makes PCR 7 depend on a key we would have to manage. The pool would never import. Ubuntu is the only distribution whose archive ships ZFS kernel modules signed with the distro key that shim already trusts, so the earlier per-cloud distribution choice had to go.

## The fixes

### 1. Immutable, measured root; secrets only on the sealed pool

The root filesystem is built as a read-only dm-verity volume. The kernel refuses any block whose hash does not match the tree, and the root hash is on the kernel command line. GRUB measures the command line into PCR 8 and the kernel and initramfs into PCR 9, so the root hash, kernel, and initramfs are all in the TPM's record of the boot. The seal policy covers PCRs 0, 2, 4, 7, 8, 9, 14, and 15. PCR 15 is unused by firmware and the bootloader, so at unseal time it still holds its reset value of all zeros, and the policy is computed against that value. This works with the stock distro-signed shim, GRUB, and kernel on all four clouds and needs no custom Secure Boot keys.

Both keys the system depends on, the ZFS pool key and a 32-byte HMAC seed, are sealed in the TPM under that policy and unsealed in the initramfs before the pool is imported. The moment both unseals have succeeded, before the pool is even looked for, the initramfs extends PCR 15 with a fixed value. Because PCR 15 is part of the policy, the policy no longer matches, so nothing that runs later in the boot can unseal the blobs again, including a root process. The timing matters: between a successful unseal and the extend the policy is still satisfiable, so the extend happens as early as the keys are out of the TPM, and the unseal script's exit path extends PCR 15 itself if it fails with the blobs present and the phase still open. A failure in the initramfs after unsealing (a detached data disk, say) therefore cannot leave the TPM in a state where the blobs could be opened by whoever reaches the console next, and in any case the initramfs has no console to reach: the kernel command line carries `rd.shell=0 rd.emergency=reboot` and the dracut module masks `dracut-emergency.service`, `emergency.service`, `emergency.target`, `rescue.service` and `rescue.target` inside the initrd and leaves out `sushell` and `rdsosreport`, so a failed boot reboots rather than dropping to a shell.

The root filesystem holds code and static configuration only. Every secret and every piece of mutable state lives on the encrypted ZFS pool: the HMAC seed is consumed from tmpfs and never written to disk, per-container keys are derived on demand, and the dnsclient configuration, box identity key, Docker data root, MariaDB data, nginx vhosts, and `/var` are all on the pool. `/etc` is a tmpfs overlay that resets every boot.

Sealing happens on the first boot of each production instance, not at build time, because a sealed blob is bound to one TPM. On first boot the initramfs finds no sealed blobs, generates both keys, creates the pool on the data disk, seals both keys to the local TPM under the policy computed from the current PCR values, and writes the blobs to `/boot/safebox/`. A tampered image would seal to its own PCR values, but every announce the box publishes carries a TPM quote, and a relying party accepts an announce only when the quote's PCR values equal the blessed set for the image root hash it names, so a tampered box announces into silence.

Two checks keep the first-boot path from being forced on a box that is not new. First, before generating anything, the initramfs runs `zpool import -d /dev` as a scan and refuses to continue if a pool named `safebox-pool` is visible on any attached disk: deleting `/boot/safebox/*` offline to make the script re-seal fresh keys under PCR values of the attacker's choosing leaves the real pool on the data disk, and a first boot is only legitimate when no pool exists anywhere. Second, the first boot writes a random 16-byte `first-boot-id` both to `/boot/safebox/first-boot-id` and to the pool as the ZFS user property `safebox:firstboot` on the root dataset, and every later boot refuses to continue if the two differ, which is what a `/boot` partition transplanted from another instance looks like. The first boot also keeps a copy of the PCR values it sealed under at `/var/lib/safebox/boot/pcr-values-first-boot.txt` on the pool, so the operator can read them back later through the attested health endpoint and compare them with the build's `expectedPcrs`.

This closes the disk swap on the same VM (PCR 8 or 9 changes, or verity fails at the first modified block), the snapshot-and-relaunch elsewhere (different TPM), editing the data disk (encrypted, key sealed), and every "get root later through a bug" path, because root on a verity filesystem cannot persist anything and the keys cannot be unsealed once boot has passed the sealed phase.

#### Why Ubuntu on every cloud

All four images are built from Ubuntu 24.04 LTS (noble). Secure Boot is a precondition for the whole chain above: PCR 7 records the Secure Boot state and the certificates used to verify shim, GRUB, and the kernel, and `lockdown=integrity` relies on it to refuse unsigned code in the kernel. Under Secure Boot the kernel loads only modules signed by a key it trusts. ZFS is not in the mainline kernel, and Ubuntu is the only distribution that ships prebuilt ZFS modules in its archive signed with the same distro key that shim and the kernel already trust. Every other candidate would have meant a DKMS build with a locally generated Machine Owner Key, which puts a signing key on the build host, changes PCR 7 to depend on that key, and makes the measured boot only as trustworthy as the host that held it. Standardising on Ubuntu removes that key and the per-distribution package maps with it.

The consequence for the repository is one installer. `common/base/install-base.sh` builds the base for every cloud and takes the kernel flavour as its only per-cloud input: `linux-aws`, `linux-gcp`, `linux-azure`, or `linux-oracle`. Each flavour is Canonical's signed kernel with that cloud's paravirtual drivers; the ZFS module package matches the flavour. The per-cloud `install-base.sh` files that remain are shims that set the flavour and call the common installer.

### 2. No cloud-init; a first-boot unit that reads data and never runs it

cloud-init is removed from every image. `safebox-firstboot.service` replaces it: a small script that reads exactly three named values from the metadata service, `safebox-id`, `owner-pubkey` and `launch-authorization`, validates their shape, writes them to the pool, and exits. It does not run scripts, create users, set passwords, or install keys. Launching an instance from the image with hostile user-data does nothing.

Nothing in the metadata is a secret and nothing is exchanged for a credential. `owner-pubkey` is the owner's Safenet Ed25519 public key. `launch-authorization` is an OCP claim signed by that key, `{type: "launch_authorization", safeboxId, ownerPubkey, notBefore, expiresAt, nonce}` with a window of at most 24 hours, saying that this owner authorizes one launch of this safebox id. On first boot dnsclient generates its own Ed25519 keypair, which is the box's identity from then on, and publishes a signed `safebox_announce` claim that carries the authorization, the image root hash, a TPM quote whose nonce is bound to the authorization, and the memory-encryption report (see "Decentralized announce"). Anyone who later reads the user-data from the console or from a snapshot gets a public key and an authorization that has expired, and could do nothing with a live one either: it is tied to one safebox id, and a box launched with it announces under its own fresh key, in public, with its own quote.

The build's last step before capture deletes the build operator account, removes home directories, shell history, cloud-init and agent state, SSH host keys, and logs; locks every password; sets every shell to `nologin`; and refuses to capture if any `/etc/shadow` entry is not `!` or `*`.

### 3. Console and GRUB

On the image: a GRUB superuser with a PBKDF2 password, `GRUB_TIMEOUT=0`, `GRUB_TIMEOUT_STYLE=hidden`, `GRUB_DISABLE_RECOVERY=true`; `rescue.service`, `emergency.service`, `console-getty.service`, `debug-shell.service`, and the `serial-getty@.service` and `getty@.service` templates are masked on the root, and the same emergency and rescue units are masked inside the initramfs with `rd.shell=0 rd.emergency=reboot` on the command line (fix 1); `kernel.sysrq=0`. The ESP holds shim, `grubx64.efi` and the stub `grub.cfg` and nothing else: `fbx64.efi` and `mmx64.efi` are left out so shim loads GRUB directly on every boot and PCR 4 does not depend on the firmware's NVRAM state. With fix 1 in place the GRUB password is a second layer: editing the command line changes PCR 8, so an attacker who gets past GRUB lands in a shell on a read-only root with no keys and a pool that will not open.

At the cloud level, Terraform and the instructions disable the serial console where a setting exists and document the account-level policy that denies re-enabling it. These stop mistakes rather than insiders; the on-image measures are what hold.

### 4. Cloud agents and extensions

The agent packages are removed outright: `walinuxagent` on Azure, `oracle-cloud-agent` and `oci-utils` on OCI, `amazon-ssm-agent` and `ec2-instance-connect` on AWS, `google-guest-agent`, `google-osconfig-agent`, and `google-compute-engine-oslogin` on GCP. Package manager pins make reinstallation fail. The build fails if any is present. Terraform sets OCI `agent_config` with all plugins disabled and GCP `serial-port-enable = "FALSE"`. The Azure image is published to a Compute Gallery with `SecurityType = TrustedLaunch`, because plain managed images cannot launch Trusted Launch VMs. Azure's `provisionVMAgent = false` and `allowExtensionOperations = false` cannot be set: they live in `osProfile`, and Azure rejects `osProfile` on a VM created from a Specialized image, which is the only kind this build can produce (there is no agent to generalize with). The control on Azure is therefore agent removal plus Azure Policy with effect `deny` on `Microsoft.Compute/virtualMachines/extensions`, on `Microsoft.Compute/virtualMachines/runCommands`, and on safebox-tagged VMs with boot diagnostics enabled. The module defines and assigns those policies at resource-group scope when `manage_deny_policies = true`; with the default `false`, the operator assigns them from `azure/INSTRUCTIONS.md`, preferably at subscription scope. The red-team script treats a policy deny or an agent-not-present error as the pass condition and an authorization failure on the tester's own call as a skip, never a pass.

### 5. Container to host root

`safebox-infra` is not in the `docker` group. Every privileged operation goes through a root-owned wrapper script at a fixed path, and the sudoers file allows exactly those paths with no argument wildcards. dnsclient, the one process that talks to the public internet and holds the box's identity key, runs as its own user `safebox-dns` (uid 992) rather than as the HMAC key holder, and may sudo only the TPM quote wrapper. The HMAC seed itself is never readable by uid 990 on disk: it stays root 0400 in `/run/safebox/` and reaches the system component through systemd's `LoadCredential=`. The wrappers build the full argument list themselves and validate every input against a strict pattern. `dnf install`, `dnf remove`, and `dnf upgrade` are removed from the privileged surface; on a verity root they cannot work, and the `/system` endpoint returns `NOT_SUPPORTED` for them with a pointer to the image rotation process.

### 6. Metadata service

An nftables rule in the `DOCKER-USER` chain drops all container traffic to the metadata address. A host rule allows the metadata address only for root and `safebox-infra`. OCI disables the legacy endpoints. AWS keeps the hop limit at 1 as a second layer. The same table carries the host's inbound policy: an `input` chain with policy drop that accepts loopback, established and related traffic, ICMP, TCP 80, 443 and 8443, and DHCP replies, and nothing else. Port 80 is open at the host because nginx binds it for ACME HTTP-01; whether the internet can reach it is the cloud firewall's decision (`allow_http`). `docker.service` carries `Requires=` and `After=safebox-nftables.service` through a drop-in, and the loader script exits non-zero if either the table or the `DOCKER-USER` rule fails to install, so the daemon never starts without the firewall.

### 7. Drift

`unattended-upgrades`, `snapd`, `ubuntu-advantage-tools`, `ksplice`, `uptrack`, `dnf-automatic`, and `fail2ban` are removed. A running safebox never changes; a patched safebox is a new image with a new hash.

### 8. Hypervisor insider

Confidential compute is required, not optional. Every announce carries, next to the TPM quote, a hardware memory-encryption report: an AMD SEV-SNP attestation report (from `/dev/sev-guest` through the `SNP_GET_REPORT` ioctl, or on Azure the report the paravisor writes into the vTPM at NV index `0x01400001`) or an Intel TDX quote (configfs-tsm, falling back to the `TDX_CMD_GET_REPORT0` TDREPORT). The report is produced by the root wrapper `safebox-confidential-report` and its 64-byte `REPORT_DATA` is `sha256(nonce) || sha256(quote.message)`, so the report is bound to the exact TPM quote it travels with (on Azure the binding runs through the vTPM AK in the HCL runtime data instead, since `REPORT_DATA` there is fixed by the paravisor). A relying party (`common/attestation/verifyAnnounce.js`) checks the `REPORT_DATA` binding, verifies the report chain to the AMD root (ARK → ASK → VCEK, fetched from AMD KDS when the box does not supply a cached VCEK) or the Intel root (PCS/PCCS) through the `fetchVcek` / `verifyTdxQuote` hooks it supplies, checks that the report's `MEASUREMENT` (or TDX `MRTD`) matches the blessed image class, and only then accepts the announce.

A box launched without confidential compute gets a report of type `none`, and dnsclient refuses to announce with code `MEMORY_NOT_ENCRYPTED` and an audit line saying the box was launched without confidential compute. The only way around this is `allowUnencryptedMemory: true` in `/etc/safebox/defaults.json`, which is set at image build (`SAFEBOX_ALLOW_UNENCRYPTED_MEMORY=1`) and lives on the verity root, so it cannot be flipped from metadata, the console or the pool. Such an image is for non-confidential shapes only; its announces say `type: none` and a relying party accepts them only when it, too, has chosen `allowUnencryptedMemory`. The Terraform variables (`skip_confidential_compute` on AWS/GCP/Azure, `skip_memory_encryption` on OCI) default to false, meaning confidential compute is on by default. Set to true only for dev/test on shapes without SEV-SNP support. OCI's `confidential_compute_type` defaults to `"SEV_SNP"`. Note that OCI's plain SEV exposes no guest report, so the default image needs an SEV-SNP or TDX shape there.

### 9. Plumbing

The AWS attestation client uses NitroTPM at `/dev/tpmrm0` through `tpm2-tools`, the same path as the other three clouds, instead of the enclave-only `/dev/nsm`. Azure and OCI link their attestation clients. The dnsclient installer exists for all four clouds and the build runs it. Configuration key names match between Terraform (`owner_pubkey`, `launch_authorization`), the metadata keys (`owner-pubkey`, `launch-authorization`), the first-boot unit, and `config.js` (`ownerPubkey`, `launchAuthorization`); there is no registration token anywhere in the chain. Package pins are real Ubuntu package names, held with apt pins (`Pin-Priority: -1`) so `apt install` of a removed agent fails rather than silently succeeding.

### 10. Verification

`verify-image.sh` runs in the build chroot before capture and fails the build on any gap: agent packages present, users with shells, unlocked passwords, listeners other than nginx, cloud-init present, GRUB without a password, missing dracut module. It writes a signed inventory into the manifest chain.

`tests/redteam/<cloud>.sh` launches a box from a candidate image and attempts every vector in this document. Each attempt must fail in the expected way: a check passes only when the cloud or the box returns the refusal the design predicts (console disabled, no managed instance, no agent, policy deny, no login prompt within the timeout, no accepted announce at the relay named by `--relay-url` for a box launched under a bogus or unknown-owner authorization). A refusal of the tester's own call (AccessDenied, Unauthorized, a missing CLI extension, a validation error on the tester's arguments) is recorded as a skip, and any other failure as a fail, so a check can never pass vacuously. The job fails if any attempt succeeds or any check fails.

The container-to-metadata and container-to-Docker-socket checks cannot be driven from outside the box. The system component's `/test` endpoint starts its container with `--network none`, so a probe through it says nothing about the `DOCKER-USER` rule or the `safebox-app` network; the scripts skip these two checks. The in-host probe has two parts. First, a tenant image whose entrypoint runs `curl -sS --max-time 5 http://169.254.169.254/` and `test -S /var/run/docker.sock` and writes both results to its workspace is created as a managed container through `/containers/create` (which puts it on the `safebox-app` network with the production flags); the expected results are a timeout or connection refused, never a metadata document, and no socket. Second, on a development boot of the same image with a shell (never a production box), `nft list chain inet safebox input` must show `policy drop`, `iptables -S DOCKER-USER` must show `-d 169.254.169.254/32 ... -j DROP` above Docker's `RETURN`, and `systemctl show docker.service -p Requires` must include `safebox-nftables.service`.

### 11. Post-quantum TLS

The TLS between a Safebox and a Jet, and between Safeboxes, carries Safecloud root keys; ECDHE alone leaves recorded traffic open to a future quantum computer. Node in the image is therefore built from source against a separately built OpenSSL 3.5 (`/usr/local/openssl-3.5`, `--shared-openssl`, `enable-ktls`), and `/etc/ssl/openssl-pq.cnf` sets `Groups = X25519MLKEM768:X25519:P-256` so every Node TLS handshake offers the hybrid ML-KEM group first and falls back to classical when the peer lacks it. `OPENSSL_CONF=/etc/ssl/openssl-pq.cnf` is set in `/etc/environment` and as `Environment=` in the system, dnsclient and autovhost units. nginx also uses OpenSSL 3.5 via `LD_LIBRARY_PATH` and `OPENSSL_CONF` set in its systemd drop-in (`/etc/systemd/system/nginx.service.d/safebox.conf`); the distro package links `libssl.so.3` (same soname as 3.5), so it picks up ML-KEM at runtime and negotiates PQ groups with browsers that support them (Chrome already does; others fall back to X25519). The build installs `build-essential`, `perl` and `pkg-config` into the chroot for the two compiles and purges them afterwards (`python3` stays: `safebox-confidential-report` needs it); `verify-image.sh` asserts `gcc` is absent, that `node` reports OpenSSL 3.5.x, and that `openssl-pq.cnf` is in place. Both tarballs are pinned by sha256 in `install-base.sh` (`SAFEBOX_OPENSSL_SHA256`, `SAFEBOX_NODE_SHA256`), and the versions and digests are recorded in `base.json`. Verification on a built image (full text in `docs/PQ-TLS.md`):

```bash
node -e "console.log('OpenSSL:', process.versions.openssl)"            # 3.5.x
/usr/local/openssl-3.5/bin/openssl list -kem-algorithms | grep -i mlkem  # mlkem768
/usr/local/openssl-3.5/bin/openssl s_server -accept 4433 -cert c.pem -key k.pem -groups X25519MLKEM768 &
/usr/local/openssl-3.5/bin/openssl s_client -connect localhost:4433 -groups X25519MLKEM768 2>&1 | grep "Server Temp Key"
# from a box against a live Jet:
/usr/local/openssl-3.5/bin/openssl s_client -connect <jet-host>:<port> -groups X25519MLKEM768 2>&1 | grep "Server Temp Key"
```

### 12. Decentralized announce

There is no registration server and no party that approves a box. Four roles, four kinds of signed statement, and every relying party does its own verification:

- Auditors bless images. Whoever rebuilds an image from source, confirms its root hash, and reads the PCR values off a first hardware boot signs an `image_blessing` claim `{imageHash, version, pcrs, measurement?}`. A relying party decides which auditor keys it trusts and how many must agree (M-of-N through `ocpVerify.verifyThreshold`); `verifyAnnounce.buildBlessedImages` turns the claims it accepts into its blessed set. No single signature blesses anything, and nobody's blessing binds anyone else.
- Owners authorize launches. An owner holds a Safenet Ed25519 key and signs a `launch_authorization` for one safebox id with a window of at most 24 hours. It goes into the instance metadata and travels inside every announce. It is public: it proves only that this owner wanted a box with this id to start around now.
- Boxes announce to the log. On first boot, on every IP change and hourly, dnsclient publishes a `safebox_announce` claim signed by the key the box generated for itself: the authorization, the image root hash, a TPM quote whose nonce binds the authorization and the previous announce, the memory-encryption report bound to that quote by its `REPORT_DATA`, the public IP, and `prev`, the hash of the box's previous announce. The claim goes to the Safenet transparency log through the peer's gossip intake and to the DNS relays named in the image. The log stores and forwards; it does not judge.
- Relying parties verify. Anyone who wants to act on a box's existence (set a DNS record, route traffic, admit it to a mesh) runs `common/attestation/verifyAnnounce.js` against its own blessed set: box signature, owner signature and window, nonce binding, AK signature over the quote, PCRs equal to the blessed set for the named image, confidential report present and bound (and chained to the AMD or Intel root when the party supplies the fetcher). The library returns the id and box key so the party can apply the first-seen rule: the first box key seen under an id keeps it, and a later announce under the same id from another key is a second box, refused and logged. `tools/dns-relay/relay.js` is a reference relying party that does exactly this and prints the record it would set; the relay at `dns.safebots.ai` in the image's defaults is the same code and the same rules, a convenience, not an authority.

What this removes: a token that could be stolen, a credential that could be revoked by someone else, an endpoint whose availability decided whether a box existed, and a database that was the only place to look. What it keeps: a tampered image still announces PCRs nobody blessed; a box on a non-confidential shape still announces `type: none`; a box launched by someone who does not hold an owner key the relying party serves is still ignored by it; and because every announce is in the log with `prev`, an id that is claimed twice, an image that was never blessed, or an owner key that signed more launches than it should have are all visible to anyone who reads the chain, not only to the party that noticed.

## Implementation contract

Everything below is normative. A component that deviates from it is a bug.

### Repository layout

`common/` holds everything that is the same on all four clouds, which since the move to Ubuntu on every cloud is nearly everything. Per-cloud directories hold only the bootstrap and capture steps of the build script, the Terraform module, the attestation client, `INSTRUCTIONS.md`, and the red-team test. Package names, the package manager, and the installers are shared.

- `common/base/install-base.sh`: the one base installer. Takes the kernel flavour (`linux-aws`, `linux-gcp`, `linux-azure`, `linux-oracle`) as its per-cloud input; each cloud's `scripts/components/base/install-base.sh` is a shim that sets the flavour and calls it.
- `common/dnsclient/` and `common/autovhost/`: the dnsclient and autovhost components with their installers, units, and tests. The per-cloud attestation client that dnsclient loads is the only file left under `<cloud>/scripts/components/dnsclient/`.

- `common/boot/safebox-unseal.sh`: runs in the initramfs. Unseals or, on first boot, generates and seals.
- `common/boot/safebox-seal.sh`: library sourced by the unseal script; wraps `tpm2-tools` for create, seal, unseal, extend.
- `common/boot/dracut/90safebox/`: dracut module that installs the two scripts, `tpm2-tools`, `zfs`, and `veritysetup` into the initramfs and hooks the unseal script before `zfs-import`. Used on all four clouds; the image installs `dracut` in place of `initramfs-tools`.
- `common/image/build-verity-root.sh <rootfs-dir> <target-disk> <grub-password-hash>`: partitions the target disk, writes the root as a verity volume, installs GRUB with the password and the measured command line, and prints the root hash.
- `common/image/compute-expected-pcrs.sh <boot-dir> <grub.cfg> <kernel> <initrd> [<stub-grub.cfg>]`: prints the expected PCR 8 (model) and PCR 9 (exact) for a build as JSON; called by `build-verity-root.sh`.
- `common/image/cleanup-image.sh <rootfs-dir>`: the pre-capture cleanup.
- `common/image/verify-image.sh <rootfs-dir>`: the pre-capture assertions. Exit non-zero on any failure.
- `common/image/grub.cfg.tmpl`: the GRUB configuration template.
- `common/firstboot/safebox-firstboot.sh` and `safebox-firstboot.service`.
- `common/attestation/tpmQuote.js` (quote parsing and AK verification), `ocpClaim.js` (Ed25519 OCP claims: launch authorizations and announces), `verifyAnnounce.js` (the relying-party verifier and `buildBlessedImages`), with `test/testVerifyAnnounce.js`.
- `tools/dns-relay/relay.js` (reference relying party) and `authorize.js` (owner key and launch-authorization helper).
- `common/net/safebox-imds.nft` and `safebox-nftables.service`.
- `common/sudo/safebox-system` (the sudoers file) and `common/sudo/bin/` (the wrappers, installed to `/opt/safebox/bin/`).
- `tests/redteam/<cloud>.sh`.

### Disk layout of the produced image

GPT with four partitions: `p1` ESP, 512 MB, FAT32, label `SAFEBOX-ESP`; `p2` `/boot`, 1 GB, ext4, label `SAFEBOX-BOOT`; `p3` root data, ext4 formatted then `veritysetup format` applied, label `SAFEBOX-ROOT`; `p4` verity hash tree, label `SAFEBOX-HASH`. The data disk is separate and is not part of the image.

### Kernel command line

`root=/dev/mapper/safebox-root ro systemd.verity_root_data=PARTLABEL=SAFEBOX-ROOT systemd.verity_root_hash=PARTLABEL=SAFEBOX-HASH roothash=<hash> systemd.volatile=overlay rd.zfs=1 rd.shell=0 rd.emergency=reboot safebox.datadisk=auto console=ttyS0,115200n8 lockdown=integrity`

`rd.shell=0 rd.emergency=reboot` means a failure inside the initramfs reboots the box instead of opening dracut's root shell on the serial console; the dracut module masks the emergency and rescue units inside the initrd as well.

`safebox.datadisk=auto` means the unseal script selects the only disk that has no partition table and no filesystem signature and is at least 50 GB. If zero or more than one disk matches, boot fails closed.

### PCR policy

`sha256:0,2,4,7,8,9,14,15`, with PCR 15 at its reset value (all zeros) at policy time. The unseal script runs `tpm2_pcrextend 15:sha256=<sha256("safebox-sealed-phase-complete")>` immediately after both unseals succeed (before `zpool import`), or on first boot immediately after both sealed blobs are written and fsynced to `/boot`, and from its exit path on any failure that happens with blobs present and the phase still open.

The build records the PCR 8 and 9 values it expects in `manifests/verity.json` under `expectedPcrs`, computed by `common/image/compute-expected-pcrs.sh`. PCR 9 is exact: sha256 of the kernel bytes and of the initramfs bytes, extended in that order from zero. PCR 8 is a model of the GRUB commands in the two configuration files the build controls; the real value also depends on the configuration embedded in the signed `grubx64.efi` and on GRUB's measurement format, so the model is confirmed against the first hardware boot's `pcr-values.txt` and it is the confirmed values that the Safenet blessing pins.

### Runtime paths

- `/run/safebox/zfs-key`: raw 32-byte key, root 0400, deleted by the unseal script after `zfs load-key` succeeds.
- `/run/safebox/hmac-seed`: raw 32-byte seed, root 0400. Lives for the life of the boot. `safebox-system.service` carries `LoadCredential=hmac-seed:/run/safebox/hmac-seed`; systemd reads the file as root at service start and exposes a copy to the service alone as `$CREDENTIALS_DIRECTORY/hmac-seed`, from which the system component derives the master and keeps it in memory. Uid 990 never has read access to the file in `/run`.
- `/boot/safebox/zfs-key.pub`, `zfs-key.priv`, `hmac-seed.pub`, `hmac-seed.priv`, `policy.digest`, `pcr-values.txt`, `first-boot-id`: the sealed blobs, the policy they were sealed under, and the identity that binds this `/boot` to its pool.
- `/var/lib/safebox/`: dataset `safebox-pool/safebox`, mode 0771 root:safebox-infra. Group write because the system component (uid 990) replaces `managed-containers.json` by rename in this directory; the "other" execute bit lets `safebox-dns` traverse to its own subdirectory, and nothing else: no other uid can list the directory, and every entry inside carries its own owner and a mode without "other" bits. Subdirectories, each owned by the uid that writes there: `containers/`, `transparency/`, `volumes/`, `succession/`, `governance/`, `nginx/` (0750 safebox-infra, per-module state, no keys); `dns/` (0750 safebox-dns:safebox-dns, uid 992: `dnsclient.json`, `identity.key` (Ed25519 private key, 0400 safebox-dns), `last-announce.json` (the most recent signed announce, head of this box's chain), `announced` (marker file), `dnsclient/state.json`); `boot/` (0750 root:safebox-infra: `pcr-values-first-boot.txt`, written by the initramfs on first boot, readable by the system component for the attested health endpoint). The initramfs unseal script creates `dns/` and `boot/` when it creates the dataset; the firstboot script creates `dns/` if an older pool lacks it. `instance.json` (root 0644) is the copy of the first-boot metadata (`safeboxId`, `ownerPubkey`, `cloud`) that autovhost reads for public-IP discovery, since uid 990 cannot read `dns/dnsclient.json`.
- `/var`: dataset `safebox-pool/var`. `/var/lib/docker`: `safebox-pool/docker`. `/var/lib/mysql`: `safebox-pool/mariadb`. `/srv/safebox/tenants`: `safebox-pool/tenants`. `/srv/zfs-clones`: `safebox-pool/clones`. `/srv/safebox/models`: `safebox-pool/models`, mode 0775 root:safebox-infra (group write because the system component, uid 990, downloads and materialises model weights there via `opsModels.js`; world-readable because every per-tenant instance uid loads models for `/embed`; the verity root is read-only so it cannot live there). Every dataset is created with `mountpoint=legacy` and mounted through `/etc/fstab` entries baked into the image (`common/image/fstab`), so each mount is a real systemd mount unit and services can order on it with `RequiresMountsFor=`.

### First boot sequence

1. Firmware, shim, GRUB (measures cmdline to PCR 8, kernel and initrd to PCR 9).
2. Initramfs: `systemd-veritysetup` opens the root. `safebox-unseal.sh` runs. No blobs in `/boot/safebox/`: refuse if `zpool import -d /dev` shows any `safebox-pool`, generate `zfs-key`, `hmac-seed` and `first-boot-id` from `/dev/urandom`, find the data disk, `zpool create` with `encryption=aes-256-gcm keyformat=raw keylocation=file:///run/safebox/zfs-key`, create datasets, set `safebox:firstboot`, seal both keys, write blobs and `first-boot-id`, fsync, extend PCR 15, copy `pcr-values.txt` to the pool. Blobs present: unseal both, extend PCR 15, `zpool import`, `zfs load-key`, check `safebox:firstboot` against `/boot/safebox/first-boot-id`. Either way, `/run/safebox/zfs-key` is deleted after load-key and `/run/safebox/hmac-seed` is left root 0400.
3. Switch root. `/etc` is a tmpfs overlay. `/var` and the other datasets mount from the pool.
4. `safebox-firstboot.service` (`ConditionPathExists=!/var/lib/safebox/dns/announced`): read `safebox-id`, `owner-pubkey` and `launch-authorization` from the metadata service, validate their shapes (`^[a-z0-9-]{3,64}$`; `^[0-9a-f]{64}$`; base64 that decodes to a `launch_authorization` claim whose `safeboxId` and `ownerPubkey` equal the other two keys, whose window is at most 24 hours, and whose `key[]` names the owner), create `/var/lib/safebox/dns/` (0750 safebox-dns) if missing, write `/var/lib/safebox/dns/dnsclient.json` (0640 safebox-dns:safebox-dns) with `safeboxId`, `ownerPubkey`, `launchAuthorization`, `cloud`. Where the box announces comes only from `dnsRelays` and `safenetLogs` in `/etc/safebox/defaults.json` on the verity root; there is no metadata override, so an operator with write access to instance metadata cannot point a box at a relay of their choosing.
5. `safebox-dnsclient.service` (`User=safebox-dns`): if `identity.key` is absent, generate it (Ed25519, 0400); verify the owner's signature on the authorization and, for the first announce, its window; obtain a TPM quote over the policy PCRs with nonce `sha256(canonical(launchAuthorization) || prev)` (`prev` is the hash of the previous announce, empty on the first; through `sudo /opt/safebox/bin/safebox-tpm-quote`) and the memory-encryption report bound to it (through `sudo /opt/safebox/bin/safebox-confidential-report`; these two are the only sudo paths `safebox-dns` has), refuse with `MEMORY_NOT_ENCRYPTED` if the report type is `none` and the image was not built with `allowUnencryptedMemory`, build the `safebox_announce` claim `{safeboxId, boxPubkey, ownerPubkey, launchAuthorization, imageRootHash, cloud, publicIp, challenge, quote, confidential, issuedAt, prev}` (`imageRootHash` from `/etc/safebox/image-hash`, falling back to `roothash=` on the kernel command line), sign it with the box key, write it to `last-announce.json`, and POST it to every Safenet peer in `safenetLogs` (`/safenet/v1/gossip`) and every relay in `dnsRelays` (`/announce`). Touch `announced` after the first delivery that any destination accepted. Re-announce on IP change and hourly, each announce chained to the last through `prev`; a delivery that fails is retried on the next heartbeat.
6. `safebox-system.service`: systemd loads `/run/safebox/hmac-seed` as a credential; the service reads `$CREDENTIALS_DIRECTORY/hmac-seed`, derives the master, starts serving.

### Metadata keys per cloud

- AWS: user-data is a JSON object `{"safebox-id": ..., "owner-pubkey": ..., "launch-authorization": ...}` fetched with IMDSv2.
- GCP: instance attributes `safebox-id`, `owner-pubkey`, `launch-authorization`.
- Azure: `user_data` (not `custom_data`) is the same JSON object, base64 on IMDS at `/metadata/instance/compute/userData`.
- OCI: metadata keys `safebox-id`, `owner-pubkey`, `launch-authorization` at `/opc/v2/instance/metadata/`.

Exactly three keys: the id (`^[a-z0-9-]{3,64}$`), the owner's Ed25519 public key (64 lowercase hex), and the base64 of the signed `launch_authorization` claim. None is secret. The relays and Safenet peers are not among them: they are baked into the image (`dnsRelays`, `safenetLogs` in `/etc/safebox/defaults.json`) and any such key in metadata is ignored.

### Sudoers and wrappers

The sudoers file grants `safebox-infra` NOPASSWD root for exactly these paths, with no wildcards in the command and `Defaults!<alias> env_reset, use_pty, log_output`:

- `/opt/safebox/bin/safebox-test-run <test-id> <image-ref> <clone-path>`: runs `docker run --detach --name safebox-test-<id> --network none --read-only --cap-drop ALL --security-opt no-new-privileges --pids-limit 256 --memory 2g --tmpfs /tmp -v <clone-path>:/workspace:rw <image-ref>`. `test-id` must match `^[a-z0-9-]{1,40}$`, `image-ref` must be `safebox-app-[a-z0-9-]+:[a-z0-9.-]+`, `clone-path` must be `/srv/zfs-clones/<test-id>` exactly.
- `/opt/safebox/bin/safebox-test-stop <test-id>`: `docker rm -f safebox-test-<id>`.
- `/opt/safebox/bin/safebox-test-logs <test-id>`: `docker logs -f`.
- `/opt/safebox/bin/safebox-zfs <snapshot|clone|destroy|rollback> <args...>`: every subcommand validates dataset names against `^safebox-pool/(tenants|clones)/[a-z0-9-]{1,40}(@[a-z0-9-]{1,40})?$` and computes the mountpoint itself under `/srv/zfs-clones/`.
- `/opt/safebox/bin/safebox-container <create|destroy|exec> <args...>`: `create` runs `docker run` with a fixed argument list and only the container name and image ref as inputs. Docker's `userns-remap: default` stays in force (no `--userns=host`): container uid 991 is host uid `<dockremap base>+991` (100991), and `create` reads the base from `/etc/subuid` and `/etc/subgid`, `chown -R`s the tenant workspace to that id, checks that the per-container key already exists on tmpfs at `/run/safebox/keys/<name>/system.hmac` (directory 0750, file 0440, owned by safebox-infra with the mapped group; the system component writes it before calling the wrapper and rewrites it on every start), bind-mounts that directory read-only at `/run/safebox/keys` inside the container (so Safebox Node reads `/run/safebox/keys/system.hmac`), and chgrps the per-container socket to the mapped gid with mode 0660, all before `docker run`. The key is never written into the tenant workspace. `safebox-test-run` chowns the clone the same way. The system component is itself a member of `safebox-app-ns` (gid 100991) so the key and socket it recreates later carry the same group; `exec` runs `docker exec --user safebox-app --workdir /workspace safebox-app-<name> <tool> <args...>` where `tool` is one of `npm`, `pip`, `cargo`, `gem`, `composer`, `git`, `migrate`, and `args` are passed through after `--`. `migrate` is a pseudo-tool: the wrapper runs `/bin/bash /workspace/migrate.sh <run|status|rollback> [<target>]` inside the tenant's own container as `safebox-app`, with the target matched against `^[a-zA-Z0-9._-]{1,256}$`, so schema migrations run at the tenant's privilege and never on the host.
- `/opt/safebox/bin/safebox-tpm-quote <nonce-hex>`: `tpm2_quote` over the policy PCRs; needed because `/dev/tpmrm0` access is restricted to root and `tss`.
- `/opt/safebox/bin/safebox-confidential-report <report-data-hex>`: the hardware memory-encryption report (fix 8). `report-data-hex` must match `^[0-9a-f]{128}$`. SEV-SNP via the `SNP_GET_REPORT` ioctl on `/dev/sev-guest`, Azure CVM via `tpm2_nvread -C o 0x01400001`, TDX via configfs-tsm or `TDX_CMD_GET_REPORT0`; prints `{"type":"none"}` when no device exists. Never talks to the network; the VCEK is included only from a local cache.
- `/opt/safebox/bin/safebox-nginx-reload`: takes no arguments; runs `nginx -t` and, only if it passes, `nginx -s reload`. Used by autovhost (which also runs as `safebox-infra`) after it writes a vhost under `/var/lib/safebox/nginx/`.

Ten wrappers in all (the original eight plus `safebox-instance` and `safebox-keyd-reload` for per-tenant isolation). The system component and autovhost call these and nothing else through sudo. `opsSystem.js` returns `NOT_SUPPORTED` for `dnf`. A second sudoers line grants `safebox-dns` NOPASSWD root for `/opt/safebox/bin/safebox-tpm-quote` and `/opt/safebox/bin/safebox-confidential-report` alone; dnsclient needs the quote and the memory-encryption report for every announce and nothing else. A third sudoers line grants `safebox-infra` NOPASSWD root for `/opt/safebox/bin/safebox-instance` (start/stop per-tenant `safebox-system@.service` instances running as unique uids) and `/opt/safebox/bin/safebox-keyd-reload` (signal the keyd service to re-derive tenant keys after a configuration change).

### Build flow

Every cloud's `build-image.sh` follows the same sequence and differs only in the bootstrap and capture steps:

1. Bootstrap a minimal Ubuntu 24.04 (noble) root into `/mnt/rootfs` with `debootstrap` on every cloud. The build host is itself Ubuntu 24.04 with `debootstrap` and `ubuntu-keyring` installed.
2. Bind-mount `/proc`, `/sys`, `/dev`, and the repo; chroot and run `install-base.sh`, `install-system.sh`, `install-dnsclient.sh`, `install-autovhost.sh`. Installers must be chroot-safe: no `systemctl start`, no TPM access, no `zpool` commands. They enable units, write configuration, and install files.
3. Chroot and run `cleanup-image.sh`, then `verify-image.sh`. Any failure aborts.
4. `build-verity-root.sh /mnt/rootfs <target-disk> <grub-password-hash>`. After rendering `grub.cfg` it runs `compute-expected-pcrs.sh` and writes the result into `manifests/verity.json` as `expectedPcrs`.
5. Capture the target disk as the cloud's image type, with the flags that turn on UEFI, Secure Boot, and vTPM support.
6. Record the root hash, `expectedPcrs` (PCR 9 exact, PCR 8 a model to be confirmed on first hardware boot), and the image id in `manifests/`.

The build instance itself is never captured.

### Terraform

Every module launches from the image with the data disk, the two-port firewall, Secure Boot and vTPM on, the agent and console settings from fix 4, and the metadata keys from the table above. The `launch_authorization` variable is marked sensitive (to keep it out of plan output, not because it is a credential); `owner_pubkey` is plain. No module has an `ignore_changes` on metadata.

### Red team tests

`tests/redteam/<cloud>.sh <image-id>` launches an instance and attempts, in order: serial console login, GRUB interrupt via the console, cloud run-command or extension, startup-script or user-data injection followed by reboot, hostile user-data on a fresh launch, boot disk clone-edit-swap, metadata reachability from a container, Docker socket reachability from a container. Each step records PASS only when the attempt fails with the refusal the design predicts, SKIP when the cloud refused the tester's own call or the step needs something the script cannot drive (the two container probes need the in-host procedure in fix 10), and FAIL otherwise. The script exits non-zero if any step records FAIL.

## Per-tenant isolation

Everything in this section is normative and supersedes the earlier sections where they describe `safebox-system.service` as one process serving every socket. The runtime paths, sudoers and first-boot steps above still hold except where this section says otherwise.

### What was wrong

Fix 5 took docker and the HMAC seed out of uid 990's reach, but one process still served every tenant: `safebox-system.service` held the master in memory, derived every per-container key, listened on every per-container socket, and could `sudo safebox-container exec` into any container, snapshot any tenant dataset and stop any test. The wrappers validated the shape of their arguments, never who was asking, because there was only one caller. A memory-safety bug or a logic bug in a request handler, reached through one tenant's socket, was therefore every tenant's problem: the attacker got the master, every key, every socket and a root wrapper that would act on any tenant's name.

### The shape now

Three kinds of process replace the one, and no process holds more than its own role needs.

`safebox-keyd.service` (`common/keyd/safebox-keyd.js`, root) is the only process that ever holds the master. It receives the seed through `LoadCredential=hmac-seed:/run/safebox/hmac-seed`, derives the master in memory, reads `/var/lib/safebox/managed-containers.json` and writes one key directory per declared container to tmpfs: `/run/safebox/keys/<name>/system.hmac` (0440, owner the tenant's instance uid, group the mapped app gid, what the container reads through its read-only bind mount) and `/run/safebox/keys/<name>/instance.hmac` (0400, owner the instance uid, what the tenant's instance reads). Both hold the same value, the per-container key `HKDF(master, salt = keyEpoch, info = "safebox-container-<name>-v1")` the design has always used. It also writes `/run/safebox/keys/_operator/control.hmac` (0400 safebox-infra), the operator's control-socket key `HKDF(master, zero salt, info = "safebox-operator-control-v1")`. Keyd listens on nothing, takes no request from anyone, and on SIGHUP re-reads the file, writes keys for new tenants and removes the directories of tenants that have gone. A config file that fails to parse leaves every existing key as it is. The master never leaves the process; no file, socket or API carries it. Keyd also sets up the runtime directories the instances rely on: `/run/safebox` becomes 0751, `/run/safebox/containers` is 1771 root:safebox-sys (sticky, so each instance can create and remove only its own socket), `/run/safebox/keys` is 0751 root.

`safebox-system@<name>.service` is one tenant's instance of the system component. It runs as `safebox-sys-<name>`, a uid in 20000..29999 recorded as `instanceUid` in that container's declaration, with primary group `safebox-sys` (gid 993) and supplementary groups `safebox-app` and `safebox-app-ns` only. `Environment=SAFEBOX_TENANT=<name>` puts `server.js` in tenant mode: it reads exactly `/run/safebox/keys/<name>/instance.hmac`, listens on exactly `/run/safebox/containers/<name>.sock`, keeps only its own declaration in memory (from `/var/lib/safebox/tenant-config/<name>.json`, a 0644 one-entry copy the operator writes, because the operator's `managed-containers.json` is 0640 and unreadable to it), refuses every control route (`/containers`, `/models`, `/volumes`, `/succession`) and does not serve the transparency log. Its `ReadWritePaths` are `/srv/safebox/tenants/<name>`, `/srv/zfs-clones`, `/var/lib/safebox/tenants/<name>` and `/run/safebox/containers`; the rest of the filesystem is read-only to it under `ProtectSystem=strict`, and everything owned by `safebox-infra` or another instance uid is unreadable by DAC. Its sandbox lines are the same as the operator's. A compromise of this process yields that tenant's key, that tenant's socket and the tenant-side wrappers, which refuse any other tenant's name.

`safebox-system.service` is the operator instance, kept under the old unit name to limit churn. It runs as `safebox-infra` (uid 990) with no supplementary groups, serves `/run/safebox/control.sock` (0600) only, authenticates with the operator key, and owns `managed-containers.json`, `/containers`, `/models`, `/volumes`, `/succession` and the transparency log. It carries no `LoadCredential=` and holds no master and no tenant key: it is not in `safebox-app-ns`, so even the group-readable `system.hmac` files are opaque to it. At startup it runs `safebox-instance start` for every declared container, since the instances are not enabled units and their users are recreated each boot. Succession now escrows the operator key, the only key this process has; the master is reconstructed on a successor from the sealed seed, never from an escrow.

### Users and groups

`install-base.sh` creates the group `safebox-sys` (gid 993) in the image and takes `safebox-infra` out of `safebox-app-ns`: the tenant instances receive that group through `SupplementaryGroups=` in their unit, and operator membership would make every tenant's group-readable `system.hmac` readable to it. The instance users cannot be baked in: tenants are declared at runtime and `/etc` is a tmpfs overlay, so they would vanish at reboot. `safebox-users.service` (`common/keyd/safebox-users.sh`, root, oneshot, before keyd and the instances) reads `managed-containers.json` and for each declared container runs `useradd -r -u <instanceUid> -g safebox-sys -s /usr/sbin/nologin -d /nonexistent safebox-sys-<name>` idempotently, refusing if the name exists under another uid or the uid is taken, and creates `/var/lib/safebox/tenants/<name>` (0750 `<uid>:safebox-sys`). The same script runs from `safebox-instance start` after the operator declares a new container. `verify-image.sh` fails the build if any `safebox-sys-*` user is baked into the image or `safebox-infra` is a member of `safebox-sys`.

### Wrappers derive the caller

Every wrapper sources `/opt/safebox/bin/safebox-caller.sh` (0644 root, not in sudoers). sudo sets `SUDO_UID` to the invoking user's real uid after `env_reset` has discarded the caller's environment, so the value cannot come from the caller; the library maps it to a passwd name and from there to a tenant (`safebox-sys-<name>`) or the operator (uid 990). The arguments never say who is asking.

- `safebox-container exec <name> …` requires the caller to be the tenant instance for `<name>`; `create` and `destroy` require the operator. `create` also creates the dataset `safebox-pool/tenants/<name>` with fixed options if it does not exist.
- `safebox-zfs` requires a tenant caller and, for every dataset named in an argument, that it belongs to that tenant: `safebox-pool/tenants/<x>` belongs to tenant `<x>` by name; `safebox-pool/clones/<id>` belongs to the tenant recorded in the ZFS user property `safebox:tenant`, which the wrapper's own `clone` subcommand sets and nothing else can set. A clone of another tenant's test, a clone with no property, or a prefix-sharing tenant name (`foo` against `foo-bar`) is refused before `zfs` runs. Test ids are still `<tenant>-<12 hex>` for attribution in listings, but ownership is the property, not the prefix.
- `safebox-test-run` requires that `safebox-pool/clones/<test-id>` carries the caller's property and labels the container `safebox.tenant=<tenant>`; `safebox-test-stop` and `safebox-test-logs` require that label to match the caller.
- `safebox-instance <start|stop> <name>` (operator only) runs `safebox-users.sh`, starts or stops `safebox-system@<name>` by a fixed unit template, and on start waits up to fifteen seconds for the instance's socket to appear.
- `safebox-keyd-reload` (operator only, no arguments) runs `systemctl kill -s HUP safebox-keyd.service`.

The sudoers file now has three grants and no wildcards: `%safebox-sys` gets the tenant-side wrappers (`safebox-test-run`, `safebox-test-stop`, `safebox-test-logs`, `safebox-zfs`, `safebox-container`), `safebox-infra` gets the operator-side ones (`safebox-container`, `safebox-instance`, `safebox-keyd-reload`, `safebox-nginx-reload`, `safebox-tpm-quote`, `safebox-confidential-report`), and `safebox-dns` is unchanged. `safebox-container` is on both lists because the wrapper decides which subcommand each caller may use. Ten wrappers in all.

### Container lifecycle

`POST /containers/create` on the control socket: allocate the lowest free `instanceUid` and a `keyEpoch`, write the declaration to `managed-containers.json` and the one-entry copy to `tenant-config/<name>.json`, `sudo safebox-keyd-reload` (keyd writes the key directory), `sudo safebox-instance start <name>` (user, state directory, unit, socket), then `sudo safebox-container create <name> <image-ref>` (the wrapper refuses without the socket and the key). Any failure rolls the earlier steps back. `POST /containers/destroy` stops the instance, removes the declaration and the copy, reloads keyd (which removes the key directory), and removes the container. The operator sends no key anywhere and never sees one.

### Paths added or changed

- `/run/safebox/keys/<name>/instance.hmac`: 0400 `<instance uid>`, the tenant instance's copy of its key. `system.hmac` is now owned by the instance uid rather than `safebox-infra`.
- `/run/safebox/keys/_operator/control.hmac`: 0400 `safebox-infra`, the operator key.
- `/run/safebox/containers`: 1771 root:safebox-sys. `/run/safebox`: 0751 root (the seed inside stays 0400 root).
- `/var/lib/safebox/tenants/<name>`: 0750 `<instance uid>:safebox-sys`, the instance's state directory; the parent is 0751 root so no instance can list or reach another's.
- `/var/lib/safebox/tenant-config/<name>.json`: 0644, the one-entry declaration copy; the directory is 0751 `safebox-infra`.
- `/var/lib/safebox/governance/`: 0751, and `governance-keys.json` 0644, because every tenant instance verifies governance claims for `/system` and the registry holds public keys only.
- `/srv/safebox/models`: 0775 root:safebox-infra instead of the previous 0770, because every tenant instance (each running as its own uid) loads models from it for `/embed`; weights are public.
- `managed-containers.json` gains `instanceUid` per container.

### Known consequences

Each tenant instance has its own ephemeral attestation identity, so `/attestation` on a per-container socket answers for that instance. Test teardown on `/containers/destroy` now happens in the tenant instance's own shutdown path (`safebox-instance stop`) rather than in the operator. A container declared before this change has no `instanceUid` and is skipped by keyd, `safebox-users` and the operator's startup; it must be destroyed and re-created through `/containers/create`. The in-host probe in fix 10 is unchanged.

### 12. DNS nameserver as measured host service

Knot DNS is installed in the base image and activated only on boxes with the nameserver role via `safebox-nameserver-role.target`. Each nameserver generates its own DNSSEC signing keys (ZSK/KSK) in the TPM via tpm2-pkcs11, following RFC 8901 multi-signer DNSSEC — no signing key material is shared between boxes. The zone is a pure function of registry state (box announces + name claims) compiled by `safebox-zone-compiler.service` every 60 seconds. Failover is automatic: when a box stops attesting, the zone recompiles with the failover box's IP within one TTL. Port 53 (TCP+UDP) is open in the host firewall; Knot binds it only when the nameserver role is active.

The `safebox-nameserver` service user (uid 994) runs with `NoNewPrivileges=true`, `ProtectSystem=strict`, and `CapabilityBoundingSet=CAP_NET_BIND_SERVICE`. Its writable paths are limited to `/var/lib/safebox/knot` and `/run/knot`. The TPM PKCS#11 store lives at `/var/lib/safebox/knot/pkcs11/`, readable only by uid 994.

A delegation monitor (`safebox-delegation-monitor.timer`, every 6 hours) checks DS and NS records at the parent, verifies all nameservers report the same SOA serial, and watches Certificate Transparency logs for unexpected certificates.

See `docs/DNS-ARCHITECTURE.md` for the full design.
